# 验证与平台集成

本地合并版补充流程；来源见 [sources.md](sources.md)。

## 证明实际交付

- 工程 / 依赖变化：运行项目 Gradle Wrapper 对应构建任务；Windows 使用项目支持的 gradlew.bat。初始化时记录成功的版本与命令。
- 状态 / 业务逻辑变化：验证输入、失败 / 取消和恢复，复用已有测试框架与样本。
- UI 变化：预览用于布局；系统栏、键盘、手势、生命周期或 shader 需要相应模拟器 / 真机证据。
- 性能变化：同一设备、构建类型、数据下比较帧耗时或内存；只针对已定位或任务要求的性能问题扩大分析。

不为普通页面改动安装整套测试、覆盖率和依赖注入框架。编译通过不等于设备行为通过，也不等于 60fps。

## 性能定位

分辨工作发生在 composition、layout 还是 draw。仅影响绘制的高频值尽量在绘制 / graphicsLayer lambda 读取，避免整页逐帧重组；真实测量变化仍需布局。

在瓶颈处检查主线程 I/O、大对象分配、无界预取、图像解码和 shader / layer 重建。不仅凭重组次数判断性能，不用不真实的稳定性注解“优化”。

## Rust / JNI / UniFFI（项目采用时）

- 明确两端各自拥有的数据、运行时、缓存与文件，保留已有业务边界。
- 先验证 DTO、异步结果、错误和取消往返。内部 trait 与可绑定服务对象分别设计。
- 确认图片输出是压缩字节、像素缓冲或文件，以及谁释放资源；测量复制与解码次数，不承诺自动零拷贝。
- 验证取消、离场、会话变更和资源释放的关联；一次调用成功不足以证明生命周期正确。
- 构建覆盖项目承诺的 ABI；模拟器可运行不代表真机 ABI 打包正确。

## 复用、移植与重构前的性能评估

先检查成熟实现能否映射已有模型、数据库和生命周期，再选择直接依赖、提取模块、移植或重构。记录候选来源和固定提交，核对许可与新增依赖；不要为了复用一个算法搬入整套宿主。

比较热路径中的串行等待、并发上限、序列化、大字节复制、重复解码、整章驻留，以及新增运行时的包体、初始化、线程和常驻内存。语言、重组计数或社区宣传不是性能结论。

必要时做最小原型，在同设备、构建、数据、缓存条件与并发量下与现有路径或最小适配基线比较相关耗时、帧数据和峰值内存。先记录结论与取舍，再正式移植；没有测量的数据标为假设。普通修复不因此扩展成全项目跑分，也不恢复用户已暂停的专项。
