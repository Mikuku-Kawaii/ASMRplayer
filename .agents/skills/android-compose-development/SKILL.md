# Android Compose Development

将 Compose 实现、导航和 edge-to-edge 作为一条工作流处理。按项目实际技术栈实施，不强制引入架构、依赖注入框架或迁移导航库。

本技能为经编辑合并版本；来源、版本与保留的许可证见 [sources.md](references/sources.md)。

## 执行范围与停止条件

用户当前任务和项目规则优先于本技能及参考中的默认检查流程。若项目规定用户自行测试，本轮只做实现与源码检查，不新增或执行测试、设备 / 视觉 / 性能验证，不把它们补成 TODO 或新台账；明确恢复某项后才在该范围开展。技能文档更新只检查结构、引用与冲突。已完成目标且没有具体范围内缺口时交付，不因风格偏好反复重做；保留数据完整性、鉴权、迁移、资源释放和既有可访问能力。

## 确定范围与环境

阅读项目约定、构建配置和涉及的页面。确定任务是规划、审查、实现还是修复；仅规划或审查时不修改实现，遵守用户限定的文件范围。

从现有配置确定 minSdk、targetSdk、compileSdk、AGP / Kotlin / Compose、导航版本及目标设备。已有项目复用设置；新工程选择经构建验证的兼容组合。引用新 API 前核对依赖和官方文档，不为单个界面效果擅自提高 minSdk。

## 实施

1. 找到状态所有者、调用链及实际失败场景，明确需要保留的行为。
2. 新页面先形成入口、内容、加载 / 空 / 错误与返回的可用闭环，再补所需动效。局部修复不扩建整套框架。
3. 页面渲染状态和上报操作；有生命周期的业务任务放在适当的状态持有者，避免 composition 中直接执行 I/O。
4. 同时处理改动依赖的导航、状态恢复、键盘 / 系统边距和无障碍语义；点击区域不能依赖装饰像素。
5. 按当前授权完成源码检查及允许的构建 / 验证；暂停测试时报告实现和已知缺口，不自动增加验证任务。源码或编译结果不代表视觉、性能或手势已验收。

## 设计判断

- 尊重用户视觉方向；Material 组件是实现工具，不自动把自定义设计替换成默认 Material 外观。
- 性能优先：接入成熟实现前评估模型、生命周期和依赖成本，结合已有证据选择直接复用、提取、移植或重构；需要测量且已获授权时才运行最小对照，未测明确为成本假设；不按语言预设快慢。
- 不以“更现代”为理由重写 Nav2、MVVM 或既有数据库。确有需求缺口或明确迁移任务时才迁移。
- 路由传稳定标识，业务层重新读取数据；不要传 Bitmap、大型业务对象或凭据。
- 多账号 / 多空间应用按业务身份划分路由、缓存和异步结果，不能只换主题色。没有此需求的项目不强加隔离架构。
- 组件接受必要状态、回调和常规 Modifier；不为一次使用建立通用组件库。

报告行为变化、实际验证结果和未验证部分。
